# 운영 런북: 결과가 확정되지 않은 이체

자동이체나 수동 이체의 결과를 시스템이 자동으로 확정하지 못했을 때 운영자가 할 일입니다. 배경은 [ADR 003](adr/003-no-retry-reconcile.md)과 [auto-transfer.md](auto-transfer.md)에 있습니다.

> 실제 운영 환경에서 이 절차를 수행해 본 적은 없습니다. 코드 동작을 기준으로 작성했습니다.

## 언제 보나

| 신호 | 의미 |
|---|---|
| 웹훅 알림 `[Billage 자동이체] 결과 불명 N건, ...` | 이번 실행에서 은행 응답을 받지 못한 이체가 있음 |
| 웹훅 알림 `[Billage 정산] 자동으로 판단하지 못한 회차 N건` | 대조에서 매칭이 2건 이상이었거나 판정할 정보가 없음 |
| 지표 `billage.transfer.unresolved` > 0 | 처리중으로 10분 넘게 남은 회차 수 |

`ALERT_WEBHOOK_URL`이 비어 있으면 알림은 로그에만 남습니다.

## 먼저 기다릴지 판단

결과 불명이 났다고 바로 손댈 필요는 없습니다. 다음 자동이체 실행(10시, 14시, 18시) 시작 시 대조가 먼저 돌면서 대부분 자동으로 확정됩니다.

사람이 볼 것은 아래 둘입니다.

- 정산 알림(`자동으로 판단하지 못한 회차`)이 온 회차
- 대조를 거쳤는데도 처리중으로 계속 남아 있는 회차

## 절차

### 1. 미해결 목록 조회

```bash
curl -H "X-Ops-API-Key: $OPS_API_KEY" \
  https://{host}/api/v1/ops/transfers/unresolved
```

처리중으로 10분 넘게 남은 회차가 나옵니다.

| 필드 | 쓰는 곳 |
|---|---|
| `scheduleSeq` | 확정 API 경로 |
| `contractId`, `installmentNo` | 사용자 문의 대응 |
| `amount` | 거래내역에서 찾을 금액 |
| `requestedAt` | 이 시각 이후 거래만 보면 됨 |
| `transferMemo` | 거래내역 적요에서 찾을 표식 (`BL{scheduleSeq}`) |

### 2. 채무자 계좌 거래내역 확인

`requestedAt` 이후 채무자 계좌의 출금 내역에서 `transferMemo`와 `amount`가 맞는 거래를 찾습니다.

`BL12`를 찾을 때 `BL123`을 같은 거래로 보지 않도록 주의합니다.

| 찾은 결과 | 판단 |
|---|---|
| 1건 | 출금됨 |
| 0건 | 출금 안 됨 |
| 2건 이상 | 중복 출금 가능성. 아래 "2건 이상일 때" 참고 |

### 3. 결과 확정

```bash
curl -X POST \
  -H "X-Ops-API-Key: $OPS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"withdrawn": true, "note": "11/05 14:02 출금 확인, 거래번호 ..."}' \
  https://{host}/api/v1/ops/transfers/{scheduleSeq}/review
```

| `withdrawn` | 결과 |
|---|---|
| `true` | 회차를 납부로 확정, 상환 이벤트 기록 |
| `false` | 기한 전이면 미납으로, 기한이 지났으면 연체로 되돌림 |

`note`는 필수입니다. 무엇을 보고 판단했는지 적습니다. 회차 상태 이력에 `운영자 확인: {note}`로 남습니다.

응답의 `result`:

| 값 | 의미 |
|---|---|
| `CONFIRMED_PAID` | 납부로 확정됨 |
| `RELEASED` | 미납 또는 연체로 되돌림 |
| `SKIPPED` | 그 사이 대조나 다른 요청이 먼저 확정함. 할 일 없음 |

### 거절되는 경우

| 응답 | 이유 |
|---|---|
| 권한 오류 | 키가 틀렸거나 서버에 `OPS_API_KEY`가 설정되지 않음 (설정이 없으면 전부 거절) |
| `withdrawn` 누락, `note` 누락 | 입력값 오류 |
| "이체 요청 후 10분이 지나지 않아..." | 은행이 아직 처리 중일 수 있음. 이때 "출금 없음"으로 되돌리면 다음 실행에서 다시 출금될 수 있어 막아 둠. 10분 뒤 다시 시도 |

## 2건 이상일 때

시스템은 같은 금액의 다른 이체인지, 같은 회차가 두 번 출금된 것인지 구분하지 못합니다.

1. 두 거래의 시각과 적요를 비교합니다. 다른 회차의 표식이면 1건으로 다시 판단합니다.
2. 같은 회차가 두 번 나간 것으로 보이면, 한 번은 납부로 확정(`withdrawn: true`)하고 `note`에 중복 출금 사실을 적습니다.
3. **환불 기능은 시스템에 없습니다.** 초과 출금분은 시스템 밖에서 처리해야 합니다.

## 조회가 계속 실패할 때

정산이 거래내역 조회에 실패하면 회차를 처리중으로 두고 다음 실행에서 다시 시도합니다. 조회에는 연결 3초, 응답 5초 타임아웃이 있어서 은행이 느려도 뒤의 자동이체는 계속 진행됩니다.

여러 실행에 걸쳐 실패가 이어지면 SSAFY 금융 API 상태를 먼저 확인합니다.

## 확인 후 보는 곳

- 지표: `/actuator/metrics/billage.transfer.unresolved`가 줄었는지 (actuator는 운영자 키가 아니라 로그인 인증이 필요합니다)
- 이력: `repayment_schedule_history`에서 해당 `schedule_seq`의 마지막 행 사유가 `REVIEWED_PAID` 또는 `REVIEWED_NOT_WITHDRAWN`인지
