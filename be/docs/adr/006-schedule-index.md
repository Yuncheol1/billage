# 006. 이체 대상 조회 인덱스는 (status, due_dt) 순서로 건다

- 상태: 적용 (엔티티 선언), 운영 DB는 수동 SQL
- 커밋: `6b8abd5`

## 상황

자동이체는 하루 세 번 아래 쿼리로 대상을 찾습니다.

```sql
WHERE rs.due_dt <= :today AND rs.status = 'NONPAID'
```

`repayment_schedule`에는 계약 생성 시 모든 회차가 미리 만들어지므로, 계약이 쌓일수록 행이 빠르게 늘어납니다. 인덱스가 없으면 매번 회차 전체를 읽습니다.

## 검토한 선택지

| 인덱스 | 판단 |
|---|---|
| `(due_dt)` | 기한이 지난 회차는 납부 여부와 상관없이 전부 범위에 들어옴. 시간이 갈수록 대부분이 범위 안 |
| `(due_dt, status)` | 앞 컬럼이 범위 조건이라 뒤의 `status`로 범위를 좁히지 못함 |
| **`(status, due_dt)`** | 등치 조건으로 미납만 고른 뒤, 그 안에서 기한 범위를 읽음 |

## 결정

```sql
ALTER TABLE repayment_schedule ADD INDEX idx_schedule_status_due_dt (status, due_dt);
```

등치 조건 컬럼을 앞에, 범위 조건 컬럼을 뒤에 둡니다.

## 측정

로컬 MySQL에 회차 12만 건(계약 1만 건, 미납 5%)을 넣고 같은 쿼리를 5번 실행한 중앙값입니다.

| | 인덱스 전 | 인덱스 후 |
|---|---|---|
| 실행 시간 | 49.3ms | 5.4ms |
| 읽은 행 (EXPLAIN) | 약 96,000 | 약 4,000 |
| 조인 순서 | 계약 → 회차 | 회차 → 계약 |

## 감수한 것

- 회차 상태가 바뀔 때마다 인덱스도 갱신됩니다 (기존 키 삭제 + 새 키 삽입). 쓰기 비용은 그날 상태가 바뀌는 회차 수에 비례합니다. 쓰기 쪽 비용은 측정하지 않았습니다.
- `ddl-auto: update`는 기존 테이블에 인덱스를 추가하지 않으므로 운영 DB에는 `db/manual/20260928_add_repayment_schedule_index.sql`을 직접 실행해야 합니다.
- 측정은 로컬 환경 한 번의 결과입니다. 데이터 분포가 다르면 수치는 달라집니다.
