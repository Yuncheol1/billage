# 006. 이체 대상 조회 인덱스는 (status, due_dt) 순서로 건다

- 상태: 적용 (엔티티 선언), 운영 DB는 수동 SQL
- 커밋: `6b8abd5`

## 상황

자동이체는 하루 세 번 아래 쿼리로 대상을 찾습니다.

```sql
WHERE rs.due_dt <= :today AND rs.status = 'NONPAID'
```

`repayment_schedule`에는 계약 생성 시 모든 회차가 미리 만들어지므로, 계약이 쌓일수록 행이 빠르게 늘어납니다. 인덱스가 없으면 매번 회차 전체를 읽습니다.

## 검토한 선택지

| 인덱스 | 판단 |
|---|---|
| `(due_dt)` | 기한이 지난 회차는 납부 여부와 상관없이 전부 범위에 들어옴. 시간이 갈수록 대부분이 범위 안 |
| `(due_dt, status)` | 앞 컬럼이 범위 조건이라 뒤의 `status`로 범위를 좁히지 못함 |
| **`(status, due_dt)`** | 등치 조건으로 미납만 고른 뒤, 그 안에서 기한 범위를 읽음 |

## 결정

```sql
ALTER TABLE repayment_schedule ADD INDEX idx_schedule_status_due_dt (status, due_dt);
```

등치 조건 컬럼을 앞에, 범위 조건 컬럼을 뒤에 둡니다.

## 측정

로컬 MySQL 8에 측정용 테이블을 만들고 회차 12만 건(계약 1만 건, 계약당 12회차, 미납 5%)을 넣었습니다. 조회 시간은 같은 쿼리를 5번 실행한 중앙값입니다.

| | 인덱스 전 | 인덱스 후 |
|---|---|---|
| 실행 시간 (EXPLAIN ANALYZE) | 49.3ms | 5.4ms |
| 실행 계획 | 계약 전체 스캔 → 계약마다 FK 인덱스로 회차 조회 | 회차 인덱스 범위 스캔 → 계약은 PK로 단건 조회 |
| 접근한 회차 행 | 약 96,000 (조건 통과 계약 약 8,000 × 회차 12) | 4,000 |
| 결과 행 | 3,000 | 3,000 |

인덱스가 조회를 빠르게 만든 방식은 탐색 속도가 아니라 **조인 순서**였습니다. 회차 쪽에 조건을 걸 인덱스가 생기자 옵티마이저가 계약이 아닌 회차부터 읽기 시작했습니다. 그 결과 조회 비용이 계약 수가 아니라 미납 건수에 비례하게 됐습니다.

쓰기 비용은 같은 데이터에서 회차 3,000건의 상태를 바꿔 비교했습니다 (각 3회).

| | 인덱스 전 | 인덱스 후 |
|---|---|---|
| 한 번에 UPDATE 3,000건 | 2.2 ~ 3.0ms | 3.1 ~ 7.1ms |
| 건별 UPDATE·커밋 3,000회 (앱의 실제 방식) | 33.0 ~ 39.7ms | 32.1 ~ 35.8ms |

한 번에 바꾸면 인덱스 갱신 비용이 몇 ms 늘었습니다. 앱처럼 건마다 커밋하면 커밋 비용이 대부분이라 차이가 측정 오차 안에 들어갔습니다.

## 감수한 것

- 회차 상태가 바뀔 때마다 인덱스도 갱신됩니다 (기존 키 삭제 + 새 키 삽입). 쓰기 비용은 그날 상태가 바뀌는 회차 수에 비례하고, 위 측정에서는 건별 커밋 기준으로 차이가 드러나지 않았습니다.
- `ddl-auto: update`는 기존 테이블에 인덱스를 추가하지 않으므로 운영 DB에는 `db/manual/20260928_add_repayment_schedule_index.sql`을 직접 실행해야 합니다.
- 측정은 실제 엔티티 전체가 아니라 필요한 컬럼만 둔 측정용 테이블에서 했습니다. 데이터 분포가 다르면 수치는 달라집니다.
