# 001. 이중 출금은 락 대신 회차 상태의 조건부 UPDATE로 막는다

- 상태: 적용
- 커밋: `c77c7b8`, `fa594e6`, `bfe19f0`

## 상황

같은 회차를 여러 경로가 동시에 건드릴 수 있습니다.

- 10·14·18시 자동이체
- 채무자의 수동 상환
- 채권자의 "직접 받았음" 처리
- 09:30 연체 전환

둘이 동시에 "미납이네, 이체하자"고 판단하면 한 회차가 두 번 출금됩니다.

처음에는 두 장치로 막았습니다.

- Redis 락: 회차 번호로 SETNX, TTL 30초. 팀에서 프로젝트 기간에 넣었습니다.
- 이체 시도 원장: `(schedule_seq, attempt_no)` 유니크로 시도를 한 줄씩 남기는 테이블. 2026-09-30에 추가했습니다.

설계를 다시 보면서 문제를 찾았습니다.

- **Redis 락은 TTL이 지나면 풀립니다.** 은행 응답이 30초보다 늦으면 다른 요청이 락을 잡고 같은 회차를 또 이체할 수 있습니다. 실제로 재현해 보지는 않았고, 코드를 읽다가 발견했습니다.
- **락과 원장이 따로 놉니다.** "이 회차가 지금 이체 중인가"를 알려면 Redis, 원장, 회차 상태를 모두 봐야 했습니다. 셋이 어긋나면 무엇이 맞는지 판단할 기준이 없습니다.
- 연체 전환과 수동 완료는 엔티티를 읽고 바꾸는 방식이라 락과 상관없이 이체 중인 상태를 덮어쓸 수 있었습니다.

## 검토한 선택지

| 선택지 | 판단 |
|---|---|
| Redis 락 유지, TTL 늘리기 | 몇 초면 충분한지 정할 근거가 없음. 늘려도 언젠가는 풀림 |
| JPA 낙관적 락 (`@Version`) | 상태와 무관한 필드가 바뀌어도 충돌로 처리됨. 팀원 코드의 엔티티 수정까지 영향 |
| `SELECT ... FOR UPDATE` 후 이체 | 은행 응답을 기다리는 동안 행 락을 잡고 있게 됨 (→ [002](002-transfer-outside-transaction.md)) |
| **회차 상태 조건부 UPDATE** | 채택 |

## 결정

회차에 `REQUESTED`(처리 중) 상태를 두고, 모든 상태 변경을 조건부 UPDATE로 합니다.

```sql
UPDATE repayment_schedule
SET status = 'REQUESTED', transfer_requested_dttm = ?
WHERE schedule_seq = ? AND status = 'NONPAID';
```

- 바뀐 행이 1이면 이긴 쪽, 0이면 진 쪽입니다. 진 쪽은 아무것도 하지 않고 끝납니다.
- 연체 전환(`NONPAID`일 때만), 수동 완료(`NONPAID`/`OVERDUE`일 때만), 납부 확정(`REQUESTED`일 때만)도 같은 방식으로 바꿨습니다.
- Redis 락과 이체 시도 원장은 제거했습니다.

"이체 중인가"를 회차 상태 하나만 보고 알 수 있게 된 것이 가장 큰 이유입니다. 규칙이 WHERE 절에 그대로 드러나서 코드만 읽어도 어떤 전이가 허용되는지 보입니다.

## 감수한 것

- 상태 변경을 JPQL UPDATE로 하므로 영속성 컨텍스트의 엔티티와 DB 값이 잠깐 다를 수 있습니다. UPDATE가 성공한 뒤에만 엔티티 값을 같게 맞춥니다.
- `REQUESTED`로 남은 회차는 누군가 확정하기 전까지 다시 이체되지 않습니다. 확정하는 방법은 [003](003-no-retry-reconcile.md)에 있습니다.
- 동시성은 `RepaymentScheduleConcurrencyTest`에서 MySQL 8 컨테이너로 검증합니다. 스레드 10개가 같은 회차를 동시에 선점하면 매번 1개만 통과합니다 (30회 반복). WHERE 절의 상태 조건을 빼고 돌리면 10개가 모두 통과해 테스트가 실패하는 것도 확인했습니다. 
- 버그로 조건부 UPDATE가 뚫리는 경우를 대비해, 자동 확정 상환 이벤트에 회차당 하나만 들어가도록 유니크 인덱스를 따로 작성했습니다 (`db/manual/20261013_...`). 테스트 컨테이너에서 이 SQL을 실행해 동작을 확인했습니다.
