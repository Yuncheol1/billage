# 002. 이체 API는 DB 트랜잭션 밖에서 호출한다

- 상태: 적용
- 커밋: `a5ae4b6`, `c77c7b8`

## 상황

프로젝트 기간의 자동이체는 회차 여러 건을 한 트랜잭션으로 묶고, 그 안에서 은행 이체 API를 불렀습니다.

이 구조에서는 **돈은 나갔는데 기록만 사라지는** 경우가 생깁니다.

1. 이체 API 호출 성공 (돈이 나감)
2. 같은 트랜잭션의 다른 작업에서 예외 (예: 알림 전송 실패)
3. 트랜잭션 롤백 → 회차는 다시 미납
4. 다음 실행에서 같은 회차를 또 이체

은행 호출은 DB 롤백으로 되돌릴 수 없습니다. 2026-09-08에는 알림 예외를 잡아서 롤백을 막는 것으로 1차 대응했지만, 알림 말고도 예외가 날 곳은 많았습니다.

## 검토한 선택지

| 선택지 | 판단 |
|---|---|
| 지금 구조에서 예외를 하나씩 잡기 | 새 코드가 들어올 때마다 다시 구멍이 생김 |
| 트랜잭션 안에서 이체 후 실패 시 보상 처리 | 보상 처리 자체도 실패할 수 있고, 은행 응답 대기 동안 커넥션과 행 락을 잡고 있음 |
| **세 단계로 나누기** | 채택 |

## 결정

한 회차를 세 단계로 처리합니다.

```
[트랜잭션 1] 미납 → 처리중 (조건부 UPDATE) 커밋
[트랜잭션 없음] 은행 이체 API 호출
[트랜잭션 2] 처리중 → 납부 + 상환 이벤트 기록
```

처리중을 먼저 커밋해 두면, 이체 뒤에 어떤 예외가 나도 회차는 처리중으로 남습니다. 처리중인 회차는 이체 대상이 아니므로 다시 출금되지 않습니다.

여러 회차를 한 트랜잭션으로 묶지 않고 회차마다 따로 처리합니다. 한 건이 실패해도 다른 건의 결과가 같이 롤백되지 않습니다.

## 감수한 것

- 트랜잭션 2가 실패하면 실제로는 돈이 나갔는데 회차는 처리중으로 남습니다. 이 상태는 대조로 확정합니다 ([003](003-no-retry-reconcile.md)).
- 원자성을 DB에 맡기지 않고 상태 전이 규칙으로 지키므로, 상태를 바꾸는 코드는 모두 조건부 UPDATE를 써야 합니다 ([001](001-conditional-update-claim.md)).
- 회차마다 트랜잭션을 여는 만큼 한 번에 묶어 처리할 때보다 커밋 횟수가 늘어납니다. 하루 이체 대상 규모에서는 문제가 되지 않는다고 판단했고, 측정하지는 않았습니다.
